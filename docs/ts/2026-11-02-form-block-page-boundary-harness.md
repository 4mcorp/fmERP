## 문제·원인

- 블록 높이를 차례로 채우고 공간이 모자라면 다음 쪽으로 넘기는 packing 시뮬레이션은 편집기의 **고정 간격 선**과 다르다. packing 결과만으로 기존 3mm 가이드를 검증하면 안전하다는 잘못된 결론이 나온다.
- Pretendard를 적용한 70개 필드/2열 혼합 문서를 실제 Chromium PDF로 만들었다. 고정 선의 좌표로 계산한 페이지와 PDF 마커의 첫 등장 페이지를 대조하면 3mm에서 세로 2건·가로 2건이 위험 방향이었다. 화면 좌표상 앞 쪽에 있는데 PDF는 다음 쪽으로 밀린 경우다. 해당 단언은 변경 전 exit 1로 실패했다.
- PDF의 그리기 명령 순서는 읽는 순서와 같지 않다. Skia는 같은 쪽의 grid 글자를 일반 필드 뒤에 기록한다. 파일 스트림 순서만 검사하면 실제로 존재하는 열을 잘못된 순서라고 판단한다.
- 기존 양식 전체를 저장하는 E2E는 기본 양식을 v2로 올린다. 후속 기안 시나리오가 `일반 기안v1`만 찾으면 클릭이 영원히 대기한다. 현재 양식 이름과 버전 숫자를 함께 한정하는 로케이터로 바꾸고 본문·저장·승인 단언은 유지한다. 이 실패는 이번 테스트의 상태 변경으로 발생한 회귀이며 기존 실패로 분류하지 않는다.
- 표 셀의 개행은 HTML에서 공백으로 합쳐진다. 개행 100개를 넣는 것만으로 한 쪽보다 큰 단일 행 fixture가 되지 않는다. 실제 줄바꿈 후 높이가 한 쪽을 넘는 충분한 본문을 넣어야 한다.

## 처리·재현

`FORM_PDF_ARTIFACTS=<절대 경로> pnpm exec vitest run --project unit features/completion/tests/block-render.test.ts`

- Linux는 Playwright Chromium, macOS는 설치된 Chrome을 쓴다. worker와 같은 `buildPdfHtml`, Pretendard data URI, `preferCSSPageSize: true`, `printBackground: true`를 사용한다.
- 후보 0/3/5/8/10/12mm를 비교한다. 로컬 Chrome에서 위험 방향 건수는 세로 3/2/0/0/0/0, 가로 4/2/1/0/0/0이었다. 처음 8mm를 선택했으나 Linux 서버 Chromium에서는 세로 7/5/4/2/2/0건으로 **8mm에서 2건이 다시 실패**했다. 가로는 로컬과 같았다. 두 엔진·방향에서 모두 0인 최소 최종 후보 **12mm**로 수정했다. 기존 서버 PDF 여백 14×12mm는 바꾸지 않는다. 가이드 본문 높이는 세로 257mm·가로 170mm다.
- 12mm에서 화면이 먼저 넘어간다고 예측하는 안전 방향 차이는 로컬 세로 3건·가로 8건, Linux 세로 0건·가로 8건이다. packing 시뮬레이션도 진단 정보로 남기되, 합격 단언은 고정 간격 모델에 건다. 특정 브라우저의 성공을 서버 성공으로 대체하지 않는다.
- 세로/가로 × 2/3/4열에서는 일반 표 60행, 긴 본문 30문단, 한 쪽보다 큰 단일 표 행, 수동 쪽 나눔, 문서 끝 마커를 검사한다. 각 마커의 누락·중복·순서, 일반 행/문단 시작과 끝의 동일 쪽, 표 머리글 반복, 거대 행의 여러 쪽 분할을 단언한다.
- 시험 전용 `fixtures/chromium-pdf.ts`는 생성된 Skia PDF의 page tree·Flate stream·ToUnicode CMap을 읽는다. 임의 PDF 업로드나 범용 문서 파서가 아니다. 새 의존성은 추가하지 않는다. 별도로 macOS PDFKit의 페이지별 마커와 대조하고 선택 페이지 PNG를 확인한다. 최초 8개 PDF의 모든 추출 글줄은 페이지 테두리 30pt 안쪽에 있었고 페이지별 마커는 두 추출기에서 일치했다.
- 기존 양식은 단위 시험에서 기본 7종을 왕복하고, E2E에서는 해당 시드 계정의 목록 API 전체를 열어 저장 전후 정의 일치·`validateFormSchema`/`validateFormLayout` 통과를 검사한다. 운영 DB나 모든 사용자 양식을 조회한 결과는 아니다.

## 재발 방지 규칙·한계

1. 쪽 경계를 측정할 때 실제 UI의 고정 간격 모델과 packing 모델을 구분한다. 실제 PDF의 마커 위치를 독립 기준으로 쓴다.
2. 페이지별 마커를 비교하고 grid의 파일 그리기 순서를 화면 순서라고 단정하지 않는다.
3. 거대 블록 시험에서는 마지막 마커가 실제 다음 쪽에 나타나는지도 확인한다. 단순 개행 수를 높이 증거로 쓰지 않는다.
4. 글꼴·CSS·브라우저·가이드 상수를 바꾸면 같은 하네스와 E2E 좌표 단언을 다시 실행한다. 마진을 상수 여러 곳에 복제하지 않는다.
5. 고정 선은 페이지 예측기가 아니다. 편집기의 설정 위젯·문서 크롬, 긴 표의 반복 머리글, 수동 쪽 나눔과 임의 크기 블록 때문에 모든 문서의 페이지 일치를 보장하지 않는다. 표본에서 위험 방향 0이라는 사실을 보편적 보장이나 픽셀 동일성으로 확대하지 않는다. 공식 출력은 서버 PDF다.
6. PDF 텍스트 마커만으로 모든 도형·글리프의 잘림을 증명하지 않는다. 독립 텍스트 추출·글줄 경계·래스터 확인을 함께 남긴다. 실제 OS 한글 IME·실기 터치는 사용자 확인 필요다.
