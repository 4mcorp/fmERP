# 결재 엔진은 core의 순수 함수로 상태를 계산하고, DB는 낙관적 잠금·추가 전용·outbox로 저장한다

- **순수 엔진:** `submit`, `act`, `withdraw` 등은 `(문서 상태, 행위, 행위자, 컨텍스트) → (새 상태, 이벤트, 처리 기록)`만 계산한다. 시각·ID·대결자 조회는 컨텍스트로 주입한다. 상태 값은 API·worker에서 직접 바꾸지 않는다.
- **처리 단위:** 같은 `seq`의 단계가 그룹이며 정족수(전원 또는 N명)가 채워지면 끝난다. 남은 단계는 `SKIPPED`. 다음 그룹이 `ACTIVE`가 되고, 마지막 결재 그룹이 끝나면 문서가 `COMPLETED`가 된다. 후결 단계는 흐름에서 제외되고 완료 때 `POST_PENDING`이 된다.
- **규칙 결정 (사용자 승인 2026-10-03):** 합의 부동의는 기본 반려(양식 옵션으로 의견만), 반려 대상은 기안자 기본·직전 결재 단계 옵션, 보류는 처리자가 하고 처리자·결재 관리자가 해제, 후결은 완료 뒤에도 후결 승인만 추가 기록 허용, 감사 단계는 반려 가능 여부를 옵션으로 둔다(기본 가능), 대결자·원 처리자 모두 처리할 수 있고 먼저 처리한 쪽만 반영, 전결은 이후 결재 단계를 `SKIPPED`로 하고 문서를 완료한다. 협조 단계는 부동의해도 반려하지 않는다.
- **동시성:** 변경된 단계의 `version`을 올리고, 저장은 `UPDATE … WHERE version = 읽은 값`이다. 0행이면 충돌로 거절한다. 처리 기록은 `(단계, 멱등 키)`가 유일해 같은 키 재요청은 같은 결과를 돌려준다.
- **기록:** `approval_action`은 INSERT·SELECT만 가능하다. 완료·보관·취소된 문서의 본문과 결재선은 DB 트리거가 변경을 거부한다(후결 승인 제외).
- **이벤트:** 같은 트랜잭션에서 `approval_event` outbox 행으로 저장하고 소비자는 M5·M8에서 추가한다.
- **문서번호:** 시리즈 키는 `사업자 + 렌더링된 패턴(SEQ 제외) + 초기화 기간`이다. 시리즈 행을 `SELECT … FOR UPDATE`로 잠가 한 트랜잭션에서 +1 한다.

**Considered Options:** 엔진이 DB를 직접 읽고 쓰는 방식(테스트가 느리고 규칙이 DB에 묶임), 상태 머신 라이브러리(XState — 단계 그룹·정족수 같은 도메인 규칙을 따로 얹어야 해 이득이 작음, 새 패키지 승인 필요), 이벤트 소싱(100명 이하 규모에 과함).
