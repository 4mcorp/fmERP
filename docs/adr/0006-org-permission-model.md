# 조직은 구체화 경로 부서 트리, 역할은 `membership.role` + 범위 있는 `role_grant`로 모델링한다

- **부서 트리:** `parent_id`에 더해 `depth`와 `path`(조상 id를 `/`로 이은 text)를 둔다. `ltree`는 쓰지 않는다(확장·타입 매핑 비용 대비 이득이 작은 규모: 100명 이하). `depth`·`path`는 DB 트리거가 계산하고, 최대 뎁스·같은 사업자·순환 검사와 하위 트리 갱신도 트리거가 한다. 사용자에게 보여 줄 판단과 문구는 `packages/core`의 순수 함수가 만들고, 트리거는 API를 거치지 않은 쓰기까지 막는 마지막 방어선이다.
- **역할:** 소유자·계정 관리자는 `membership.role`(owner·admin)로 두고 계정 전체 범위가 암묵적이다. 사업자 관리자·결재 관리자·감사인·인사 관리자는 `role_grant`(역할 + 범위 계정·사업자·부서+하위)로 부여한다. 모든 판정은 `packages/core`의 `can(actor, action, target)` 한 곳에서 하고, 부서 범위는 대상 부서의 `path`에 부여 부서 id가 들어 있는지로 판단한다.
- **구성원 대상 행위:** 구성원은 여러 사업자에 겸직할 수 있으므로, 계정 범위 권한이 있거나 구성원의 유효 소속 사업자 중 하나에 대한 권한이 있으면 허용한다. 관리자 역할 초대·역할 부여는 계정 관리자 이상만 할 수 있어 사업자 관리자의 권한 상승을 막는다.
- **테넌트 일관성:** 소속·역할·부서가 가리키는 사업자·구성원·직위는 `(id, account_id)` 복합 외래 키로 같은 계정임을 DB가 보장한다.
- **진행 중 결재 검사**(사업자 비활성화, 부서 폐지·삭제)는 결재 문서가 생기는 M4 전까지 항상 0건을 돌려주는 검사 지점(`apps/web/server/in-flight.ts`)만 둔다.

**Considered Options:** `ltree`(트리 질의가 간결하나 확장 의존, Drizzle 타입 지원 부족), 모든 역할을 `role_grant`로(소유자·관리자 판정이 복잡해지고 마지막 소유자 보호가 어려워짐), 사용자 정의 역할(PRD PERM-005, P2).
