# 문서·산출물 규칙

## 1. 문서 위치
| 위치 | 내용 | 수정 주체 |
|---|---|---|
| `docs/*.md` (루트) | **기준 문서**: PRD, TECH_SPEC, DEPLOYMENT_PLAN, 후보 비교 기록 | 사용자 승인 후에만 수정 |
| `docs/INDEX.md` | 색인: 규칙·문서·스킬·산출물 위치 | 산출물을 만들거나 바꿀 때마다 갱신 |
| `docs/rules/` | 구현 세부 규칙 (영역별) | 새 규칙이 확정되면 갱신 |
| `docs/plan/` | 작업 계획 | 에이전트 작성, 사용자 검토 |
| `docs/ts/` | 트러블슈팅 기록 (문제 → 원인 → 해결 → 재발 방지 규칙) | 에이전트 작성 |
| `docs/idea/` | 아이디어, 보류한 대안, 재검토 조건이 있는 항목 | 에이전트·사용자 |
| `docs/adr/` | 되돌리기 어려운 설계 결정 기록 (`domain-modeling` 스킬 형식) | 결정 시 작성 |
| `GLOSSARY.md` (루트) | 도메인 용어집 (`domain-modeling` 스킬이 관리) | 용어가 확정될 때 |

## 2. 파일 이름과 머리말
- 파일 이름: `YYYY-MM-DD-<영문-kebab-slug>.md` (예: `2026-10-03-windows-npx-mcp-enoent.md`)
- 모든 plan·ts·idea 파일은 YAML 머리말을 가진다.
  ```yaml
  ---
  title: 한 줄 제목
  date: 2026-10-03
  status: draft | in-progress | done | resolved | proposed | parked | accepted | rejected
  tags: [windows, mcp]     # INDEX 검색용. 영문 소문자
  related: [APV-061, docs/rules/database.md]
  ---
  ```
- 템플릿: 각 폴더의 `_TEMPLATE.md`를 복사해서 쓴다.

## 3. 언제 무엇을 남기나
| 상황 | 산출물 |
|---|---|
| 여러 단계·여러 파일에 걸친 작업을 시작할 때, 또는 사용자가 계획을 요청했을 때 | `plan/` — 목표, 범위(PRD ID), 단계, 완료 기준. 진행 상태를 갱신하고, 끝나면 `done` |
| 같은 오류로 시도를 **2번 이상** 반복했을 때, 도구·환경의 함정을 발견했을 때, 사용자가 실수를 지적했을 때 | `ts/` — **작업을 끝내기 전에** 작성 |
| 범위 밖 아이디어, 채택하지 않은 대안, "나중에 다시 보자"로 정한 항목 | `idea/` — 재검토 조건을 함께 기록 |
| 되돌리기 어려운 설계 결정 (DB 키 전략, 에러 형식 등) | `adr/` |

## 4. 트러블슈팅(ts) 활용 규칙
1. **작업 전:** 요청의 영역 키워드(예: `auth`, `db`, `migration`, `windows`, `mcp`, `deps`, `build`, `test`, `skills`)를 정한다. INDEX의 트러블슈팅 표에서 태그가 겹치는 항목을 모두 읽는다. 표에서 판단이 어려우면 `docs/ts/`에서 키워드를 검색한다.
2. **작업 중:** 읽은 항목의 "재발 방지 규칙"을 그대로 적용한다. 그 규칙을 어겨야 하는 상황이면 먼저 사용자에게 알린다.
3. **작업 후:** 새 함정을 만났다면 ts를 작성한다. 기존 항목과 같은 문제면 새로 만들지 않고 기존 항목에 "재발" 기록과 보강 내용을 추가한다.
4. ts의 "재발 방지 규칙"은 **다음 작업자가 그대로 따를 수 있는 명령형 문장**으로 쓴다. 예: "Windows용 MCP 설정에서 `npx`는 `cmd /c`로 감싼다."

## 5. INDEX 갱신 규칙
- plan·ts·idea·adr·rules 파일을 추가하거나 상태를 바꾸면 INDEX의 해당 표에 한 줄을 추가하거나 수정한다.
- 표에는 경로, 태그, 한 줄 요약만 적는다. 내용은 원본 파일에 둔다.
- 코드 구조가 생기면 INDEX "코드 위치" 표를 갱신한다.
