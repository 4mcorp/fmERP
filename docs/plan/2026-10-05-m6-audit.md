## 목표
감사인이 부여받은 범위의 문서를 **열람하고(열람 자체가 기록됨) 문서별 이력 타임라인으로 확인**하고, 관리자·감사인이 **감사 로그를 조회**하며 **월 1회 접속 기록 점검 결과를 남길 수 있게** 한다. 개인정보 안전성 확보조치(접속 기록 보관·점검)를 화면 수준에서 충족하는 것이 목적이다.

## 설계
### 1. 감사인 열람 기록 (AUD-010)
- 문서 상세 조회에서 열람 근거가 **`read_all`(감사인·소유자) 하나뿐**이고 참여자·참조자 등 다른 근거가 없으면 `document.audit_view`를 기록한다(행위자·문서·IP, 대외비 이상이면 등급을 `reason`이 아닌 `targetLabel`에 함께).
- 같은 사용자·문서의 중복 기록은 **10분 안에는 한 번만** 남긴다(조회 후 새로고침마다 기록이 쌓이는 것을 막음. 로그는 UPDATE 불가라 조회로 판정).
- 감사인은 처리·댓글·수신 접수 등 어떤 쓰기 API도 호출할 수 없다. 이미 권한 판정에서 막히는지 **통합 테스트로 고정**한다(화면은 버튼을 숨김).

### 2. 이력 타임라인 (AUD-011)
- `GET /api/approvals/{id}/timeline`. 열람 권한은 문서 열람과 같다(`canViewDocument`). 여기서 조회하는 것도 감사인이면 열람 기록(1번)에 포함.
- 데이터 합치기: `approval_action`(상신 이후 각 단계 처리, 대결 여부), `approval_event`, 감사 로그 중 `target=document`(`approval.create`·`line_change`·`replace_line`·`download_*`·`print`·`circulate`·`distribute`·`receive`). 시각순 정렬, 한 항목은 `{at, kind, actor, onBehalfOf?, label, detail}`.
- 표시 항목은 PRD 순서(작성 → 상신 → 단계 처리 → 결재선 변경 → 다운로드·인쇄 → 완료 → 공람). 감사 로그의 IP는 감사인·관리자에게만 보인다.
- 데이터 출처가 셋이라 **중복·누락 위험**이 있다. 같은 사건이 `approval_action`과 감사 로그에 둘 다 있으면(예: 승인) `approval_action`을 정본으로 하고 감사 로그 쪽은 제외하는 규칙을 코드와 테스트로 고정한다.

### 3. 인쇄 기록 (AUD-020)
- 브라우저 인쇄(Ctrl+P)는 서버가 알 수 없다. 문서 상세에 **"인쇄" 버튼**을 두고, 누르면 `POST /api/approvals/{id}/print-log`가 `document.print`를 기록한 뒤 인쇄 화면을 연다. `beforeprint` 이벤트가 오면 같은 호출을 한 번 한다(최선 노력). Ctrl+P·화면 캡처 같은 우회는 기록할 수 없다는 한계를 문서에 적는다.
- 완료 문서는 인쇄용 PDF(서명 URL), 진행 중 문서는 현재 화면을 인쇄한다.

### 4. 감사 로그 조회 (AUD-025)
- `GET /api/audit-logs` — 필터: 기간(필수 아님, 기본 최근 30일), 행위자, 행위 유형(prefix 목록에서 선택), 대상 종류·ID, 결과. **커서 페이지네이션**(`occurred_at, id`), 인덱스는 기존 `(account_id, occurred_at)`·`(actor_user_id, occurred_at)`로 충분한지 EXPLAIN으로 확인하고 모자라면 `(account_id, action, occurred_at)`을 추가한다.
- 권한은 `audit.read`(소유자·관리자·계정 범위 감사인). 사업자·부서 범위 감사인은 전체 로그를 볼 수 없고 문서 타임라인만 본다(Q1).
- **조회 행위도 기록**(`audit.view_log`, 필터 값 포함, 첫 쪽 요청만)한다. 로그에는 개인정보(정보주체)가 있기 때문이다.
- 화면 `/admin/audit`: 필터 바 + 표 + 상세 패널(diff·IP·UA·request id). 모바일은 표가 카드로 접힌다.

### 4-1. 보존 (AUD-024)
- 삭제·아카이브 코드를 만들지 않는다(앱 역할에 DELETE 권한도 없음). 보존 요건(접속 1년·권한 변경 3년)은 **영구 보관으로 충족**하고, 이를 `docs/rules/security.md`에 한 줄로 명시한다.

### 5. 월간 점검 (AUD-026)
- 테이블 `audit_review`: `id`, `account_id`, `period`(`YYYY-MM`, 점검 대상 달), `reviewer_membership_id`, `reviewed_at`, `memo`, `abnormal`(bool), `abnormal_note`. **INSERT·SELECT만** 허용하고 RLS를 건다. 같은 달에 여러 건이 가능하고 가장 마지막 건이 현재 상태다(정정은 새 건으로).
- 화면(`/admin/audit/review`): 점검 대상 달 목록(최근 12개월)과 상태(미점검·점검 완료·이상 있음), "점검 완료" 입력(점검자는 세션에서, 일시는 서버, 메모, 이상 여부·내용), 점검 기록은 감사 로그에도 남긴다(`audit.review`).
- **미점검 판정:** 전월 점검이 말일 이후 `audit.read` 보유자에게 필요하다. M6는 판정 함수와 API(`GET /api/audit-logs/review-status`)까지 만들고 **알림 발송은 M8**에서 이 함수를 쓴다. 지금은 점검 화면과 관리 메뉴에 "지난달 점검 필요" 배지를 보인다.
- 점검 권한은 `audit.read` 보유자 전체(Q2).

### 6. 감사 단계 보강 (AUD-001·002)
- A1에서 결재선 저장 시 감사 단계 대상 검증을 확인한다: 대상 구성원이 **감사인 역할 보유자**이거나 **감사 부서 소속**이어야 한다. 없으면 검증을 추가하고 단위·통합 테스트로 닫는다. 양식별 `auditCanReject`는 이미 구현되어 통합 테스트(의견만·반려 가능 각각)로만 닫는다.

## 완료 기준
- [ ] 단위: 타임라인 병합·중복 제거 규칙, 미점검 월 판정, 열람 근거 판정
- [ ] 통합:
  - **열람 기록:** 감사인 열람 시 기록이 남고 10분 안 재열람은 늘지 않으며, 참여자의 열람은 기록하지 않는다. 임시저장 문서는 감사인에게 404
  - **읽기 전용:** 감사인이 결재 처리·수정·접수·댓글 API를 호출하면 거부
  - **범위:** 부서 범위 감사인은 범위 밖 문서·타임라인 404, 전체 로그 조회 403
  - **타임라인:** 상신·단계 처리(대결 포함)·결재선 변경·다운로드·인쇄·완료·공람이 시각순, 중복 없음
  - **감사 로그 조회:** 필터 조합·커서, 타 계정 로그 비노출, 조회 행위 기록, 10만 건에서 1초 이내
  - **월간 점검:** 등록·재점검, UPDATE·DELETE 거부, 타 계정 격리, 미점검 판정
  - 감사 단계 대상 검증, `auditCanReject` 양쪽 동작
  - M2~M5 통합 테스트 회귀 없음
- [ ] E2E(데스크톱·360px): 감사인 로그인 → 감사함 → 문서 열람 → 타임라인 → 읽기 전용, 관리자가 감사 로그 필터 조회·점검 완료
- [ ] lint · typecheck · 전체 테스트 · `next build`
