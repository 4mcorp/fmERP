## 범위와 한계
- 대상: `packages/backup`(덤프·내보내기·색인 재구성·리허설·복원), 운영자 CLI(`apps/worker/src/cli`), worker 작업(`backup-jobs.ts`), `apps/web/server/system/backups.ts`·`account-export.ts`·`routes/system.ts`·`routes/exports.ts`, 마이그레이션 0015~0017, 완료 패키지 형식 v2(`packages/core/src/completion-package.ts`), 화면(`/system/backups`, `/admin/backups`, 설정 토글).
- `differential-review` 방법(위험 분류 → 제거된 보안 코드 확인 → 호출자·권한 경로 → 적대적 시나리오 → 재현)을 따랐다. 위험 분류: 시스템 관리자 판정·서명 URL·DB 권한·S3 경로·복원 쓰기 경로는 **높음**, 화면은 **낮음**. 모델 서브에이전트와 Semgrep은 실행하지 않았고 시나리오는 직접 만들어 통합 테스트로 재현·고정했다.
- **제거된 보안 코드: 없음.** 기존 파일에서 지워진 것은 `completion-package.ts`의 스키마 버전 상수 값 변경(1→2)과 `storage-backup.md`의 이전 3·4장 문구뿐이다.
- 로컬에서 검증하지 못한 것: 버킷 수명 주기·Object Lock, `rclone`, 컨테이너 안 Chromium, 실제 age 바이너리와의 호환(만든 파일을 `age` CLI로 열어 보지 않았다 — 라이브러리 간 왕복만 검증), 서버 하드웨어 교체 절차.

## 점검한 경로와 결과
| 경로 | 결과 | 근거 |
|---|---|---|
| **시스템 관리자 판정**: 이메일을 바꿔 시스템 관리자가 되는 경로 | 불가 | Better Auth의 `/change-email`·`/update-user` 등 자기 변경 경로가 `disabledPaths`로 막혀 있고, 판정은 `emailVerified`가 참일 때만 목록과 완전 일치(대소문자·공백 무시, 부분 일치 불가)로 통과. 단위·통합 테스트 |
| 시스템 관리자가 아닌 사용자(소유자·관리자·구성원·감사인)의 덤프 API | 404 | 존재를 알리지 않음, 통합 테스트(목록·요청·다운로드·삭제) |
| 로그인 없는 접근 | 401 | 통합 테스트 |
| 재인증 없는 덤프 요청·다운로드·삭제, 내보내기 요청·다운로드 | 428 | 계정 정책 `pinRequired=false`로 면제되지 않는 엄격한 재인증, 통합 테스트 |
| 권한 없는 사용자에게 PIN부터 요구 | 안 함 | 권한(403/404)을 먼저, 재인증(428)을 나중에 (통합 테스트) |
| 계정 관리자가 스스로 내보내기를 허용 | 거부(403) | 허용 설정은 소유자만 변경, 통합·E2E |
| 허용을 끈 뒤 관리자의 내려받기 | 거부 | 내려받을 때마다 권한 재확인 |
| 다른 계정의 내보내기 이력·파일 접근 | 404(RLS) | 통합 테스트 |
| 내보내기 ZIP의 다른 계정 데이터 혼입 | 없음 | 계정 데이터는 앱 역할(RLS)로만 읽고, 다른 계정 경로·구성원이 ZIP에 없음을 통합 테스트로 확인 |
| ZIP 경로 조작(zip slip) | 불가 | 항목 이름은 DB의 ID·사업자 코드(`[A-Z0-9_-]{1,10}`)와 `safeEntryName`(구분자·제어 문자 제거)으로 만든다, 단위·통합 테스트 |
| CSV 수식 주입 | 막음 | `= + - @` 시작 칸에 `'`, 통합 테스트 |
| 덤프 평문 노출 | 없음 | 서버에는 age 공개키만 있고 올라간 파일이 `age-encryption.org/v1`로 시작함을 확인, 다른 개인키로 복호화 불가 |
| 덤프에 세션·인증 토큰 | 제외 | `session`·`verification` 데이터를 빼고 복원본에서 0건임을 확인 |
| 개인키 취급 | 서버·로그·저장소에 없음 | CLI는 파일로 읽고 출력하지 않음, 테스트는 키를 메모리에서 생성 |
| 비밀번호의 노출 | 인자 아님 | pg 도구 접속 비밀번호는 `PGPASSWORD` 환경 변수로 전달 |
| 감사 로그 | 모두 기록 | `backup.dump`·`dump_request`·`download`·`delete_request`(계정 없음), `account.export_request`·`ready`·`download`(계정별), `backup.reindex` |
| 끝난 이력의 변조 | 차단 | 트리거(덤프는 삭제 표시만, 내보내기는 만료로만), DELETE 권한 없음, 통합 테스트 |
| 색인 재구성의 불변 트리거 우회 | 없음 | 앱 역할로 초안 → 진행 중 → 완료 순서를 재현. 소유자 권한으로 트리거를 끄는 것은 **시험에서 DB 유실을 흉내 낼 때만** 쓴다 |
| 변조된 패키지·다른 계정을 가리키는 패키지의 재구성 | 거부·보고 | manifest 해시 검증, `restore.accountId`·첨부 경로 검사, 통합 테스트 |

## 발견과 조치
| # | 위험 | 내용 | 조치 |
|---|---|---|---|
| S1 | 중간 (다층 방어 부재) | **앱 DB 역할이 완료 상태(`READY`·`SUCCEEDED`)와 저장소 키를 직접 넣은 행을 만들 수 있었다.** 지금 API는 `QUEUED`만 넣지만, 앱 코드 결함이나 SQL 오류가 있으면 다른 계정의 내보내기 파일이나 시스템 덤프 키를 가리키는 행이 생기고, 내려받기 API가 그 키로 서명 URL을 발급해 **다른 계정의 ZIP·덤프를 받을 수 있다** | **수정함.** 마이그레이션 0017 트리거 `backup_request_only`: 앱 역할은 `QUEUED` 요청만 넣을 수 있다(완료 상태·키·해시·시각 불가). 소유자·백업 역할은 막지 않는다. 통합 테스트(내보내기·덤프 각각 거부, 정상 요청 통과) |
| S2 | 낮음 | 위 S1의 코드 쪽 방어가 없었다. 키가 이 계정·덤프의 경로 밖이어도 서명 URL·태그를 만들었다 | **수정함.** 내보내기 다운로드는 `exports/{계정}/`, 덤프 다운로드는 `_system/db-dumps/`, 덤프 삭제 요청은 `_system/db-dumps/manual/` 아래의 키만 허용(아니면 409). 통합 테스트 |
| S3 | 낮음 | **첨부 키가 다른 계정 경로를 가리켜도 ZIP에 담고, 재구성에서도 그대로 받아들였다.** DB 값이 잘못되면 다른 계정의 객체가 내보내기에 섞인다 | **수정함.** 내보내기는 `docs/{이 계정}/` 밖의 첨부를 담지 않고 경고로 남긴다. 재구성은 첨부 참조가 계정 경로 밖이면 그 문서를 건너뛴다. 통합 테스트 2건 |
| S4 | 낮음 | **pg_dump가 멈추면 `RUNNING` 행이 남아 새 덤프를 막는다**(활성 행이 하나뿐인 인덱스). worker 재시작 때만 닫혔다 | **수정함.** 덤프 제한 시간(기본 90분)을 두고 넘으면 프로세스를 죽이고 `FAILED`로 기록한다. 통합 테스트(제한 후 바로 다음 덤프 시작) |

## 남은 위험·후속
- **FU-M7-1 후결 승인의 S3 기록 없음:** `post-approvals/` 키 규칙만 있고 쓰는 코드가 없다. DB를 잃으면 후결 승인 사실은 덤프의 결재 기록·감사 로그에만 있다(재구성은 완료 시점 상태로 되살림). ADR 0009 설계대로 기록하는 코드를 따로 만든다.
- **FU-M7-2 서버 API 전반의 속도 제한 없음**(M6 FU-M6-1과 같음): 시스템 관리자·소유자 전용이고 PIN 재인증이 있어 위험은 낮다. 운영 설정(Cloudflare 규칙, M8)에서 다룬다.
- **FU-M7-3 `user_identity`의 OAuth 토큰·비밀번호 해시가 덤프에 들어간다:** 덤프는 age로 암호화되지만 개인키가 유출되면 함께 노출된다. 소셜 로그인을 구현하는 **M9에서 토큰을 저장하지 않거나 최소화**하고, 그때 덤프 제외 대상을 다시 정한다.
- **CLI `--target` URL의 비밀번호가 프로세스 인자에 보인다:** 운영자가 서버에서 직접 실행하는 도구라 위험은 낮지만, 가능하면 `PGPASSWORD` 환경 변수나 `.pgpass`를 쓴다(이관 문서에 명시).
- 내보내기·덤프 크기의 한계(수십 GB)는 측정하지 않았다. 스트리밍이라 메모리는 일정하지만 시간은 선형이다.
- 로컬 검증 한계(수명 주기·Object Lock·rclone·실제 `age` CLI 호환)는 스테이징(M8)·복구 리허설(M9)에서 확인한다.
